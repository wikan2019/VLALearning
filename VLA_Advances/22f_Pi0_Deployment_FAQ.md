## 1. 能否在消费级显卡上运行？

### 参数量与显存需求

```
π0.7 核心组件:
  VLM 骨干 (SigLIP + Gemma3 4B):  ~4B 参数
  Action Expert (Flow Matching):   ~860M 参数
  高层策略 (VLM 复用):             共享参数
  世界模型 (轻量级):               ~数百M (估算)
  总计: ~5-6B 参数
```

| 精度 | 模型显存 | KV Cache + 推理 | 总需求 |
|:---|:---|:---|:---|
| FP16/BF16 | ~11 GB | ~4 GB | ~15 GB |
| INT8 量化 | ~5.5 GB | ~3 GB | ~8.5 GB |
| INT4 量化 | ~3 GB | ~2.5 GB | ~5.5 GB |

### 消费级显卡可行性

| 显卡 | 显存 | FP16 | INT8 | INT4 |
|:---|:---|:---|:---|:---|
| RTX 3060 (12GB) | 12 GB | ❌ | ✅ 勉强 | ✅ |
| RTX 3090 (24GB) | 24 GB | ✅ | ✅ | ✅ |
| RTX 4060 Ti (16GB) | 16 GB | ✅ 勉强 | ✅ | ✅ |
| RTX 4090 (24GB) | 24 GB | ✅ | ✅ | ✅ |
| RTX 5090 (32GB) | 32 GB | ✅ 充裕 | ✅ | ✅ |

### 关键瓶颈：推理速度

```
消费级 vs 服务器级推理延迟:
  RTX 4090:     ~80ms/step  → ~12Hz  → 勉强可用 (Action Chunk 缓冲)
  RTX 3060:     ~200ms/step → ~5Hz   → 太慢
  A100/H100:    ~30ms/step  → ~33Hz  → 充裕

Action Chunking 的救命作用:
  每次推理输出 50 步动作 (约 2-3 秒)
  → 即使推理 100ms/次，实际控制频率相当于 ~500Hz
  → 关键是 chunk 间的平滑衔接
```

### 已有先例

OpenPi (π0/π0-FAST/π0.5 开源版) 支持 RTX 4090 推理：
- FP16: ~15Hz
- INT8: ~20Hz
- 官方最低要求: >8GB 显存 (推理), >22.5GB (LoRA 微调)

## 2. 量化对 VLA 性能的影响

### VLA 比 LLM 更怕量化

```
LLM 输出: 离散 token (从 32000 词中选一个)
  → 量化误差只要不改变 argmax 排序，输出完全不变
  → 对量化非常鲁棒

VLA 输出: 连续动作值 (如 Δx = +0.0523m)
  → 量化误差直接叠加到动作值上
  → 0.5mm 偏差在精细操作中可能导致失败
```

### 量化性能数据 (基于 OpenVLA 等开源 VLA)

| 模型 | 精度 | 简单任务 (抓取) | 中等任务 (放置) | 精细任务 (插入) |
|:---|:---|:---|:---|:---|
| FP16 基线 | — | 85% | 72% | 45% |
| INT8 | 8-bit | 84% (-1%) | 70% (-2%) | 40% (-5%) |
| INT4 | 4-bit | 80% (-5%) | 62% (-10%) | 28% (-17%) |

### 关键发现：Action Expert 是量化瓶颈

```
VLM 骨干 (语义特征): 量化鲁棒性好，INT4 损失 <3%
Action Expert (连续动作值): 对量化极其敏感

最佳实践 — 混合精度量化:
  VLM 骨干 → INT4 (省显存)
  Action Expert → FP16 或 INT8 (保精度)
  → 总显存 ≈ INT8 水平，精细任务性能接近 FP16
```

### FAST 架构天然抗量化

```
Flow Matching (π0 原版):
  10 步迭代去噪 → 量化误差累积 → INT4 性能下降明显

FAST 自回归 (π0-FAST):
  输出离散 token → 量化不改变 token 排序就无损
  → INT4 也几乎无损 ← 边缘部署首选
```

## 3. 云端 GPU 推理方案与成本

### 核心矛盾：延迟

```
云端推理延迟链:
  上传图像 (~5-20ms) → 网络传输 (~10-50ms) → GPU 推理 (~30-80ms) → 下发动作 (~5-20ms)
  总计: 50-170ms (理想) / 100-300ms (现实)

Action Chunking 补偿:
  一次推理输出 50 步 (2.5 秒) → 执行期间不需要网络通信
  → 对折叠、擦桌等非时间关键任务完全 OK
```

### 服务商价格对比

| 服务商 | GPU | 价格 | 适合 |
|:---|:---|:---|:---|
| **AutoDL** (国内) | RTX 4090 | ~¥2-3/时 | 国内研究首选 |
| **AutoDL** | A100 | ~¥8-12/时 | 国内高性能 |
| **RunPod** | RTX 4090 | ~$0.4-0.7/时 | 海外低价 |
| **Vast.ai** | RTX 4090 | ~$0.3-0.5/时 | 最便宜 |
| **Lambda Cloud** | A100 80GB | ~$1.1-1.5/时 | 高性能 |
| **AWS/GCP/Azure** | A100/H100 | ~$3-4/时 | 企业级 SLA |

### 实际月费估算 (一台机器人 8 小时/天)

| 方案 | 月费 | 适合 |
|:---|:---|:---|
| AutoDL 4090 (国内) | ~¥600/月 | 研究团队 |
| RunPod 4090 | ~¥900/月 | 海外部署 |

### 延迟优化策略

```
1. 边缘-云协同: 本地提取视觉特征，云端只跑 Action Expert
2. 预测性推理: 执行当前 chunk 时提前请求下一个 (pipeline)
3. 就近部署: 同城数据中心 <10ms RTT
4. TensorRT/ONNX 优化: 推理速度翻倍
```

## 4. 为什么机器人控制需要低延迟？

### 能暂停等推理吗？

**部分任务可以，但物理世界不会暂停。**

| 可以等 ✅ | 不能等 ❌ |
|:---|:---|
| 静态环境操作 (折叠、擦桌) | 接住抛来的物体 (~550ms 总时间) |
| 物体不会自己移动的场景 | 倒水 (暂停时水继续流) |
| 步骤间有自然停顿的任务 | 搬运易碎品 (停顿→抖动→洒出) |
| | 人机交互 (人期望 <0.5s 响应) |

### π0 的解法：Action Chunking = "有计划的暂停"

```
时序:
  t=0ms:      推理开始
  t=80ms:     推理完成，得到 50 步 Action Chunk
  t=80-2080ms: 以 50Hz 连续执行 (不需要推理)
  t=1800ms:   提前开始推理下一个 chunk (pipeline)
  t=2080ms:   无缝切换到新 chunk
  
  → 机器人连续运动，"暂停"被隐藏在执行期间
```

### Action Chunking 的局限

```
环境变化速度 > chunk 更新速度时:
  chunk 规划 "向前伸手 50 步" → 第 10 步时人把物体移走
  → 第 11-50 步按原计划执行 → 抓空
  → 需要等下一个 chunk 才能反应

tradeoff:
  长 chunk: 省算力，但反应慢
  短 chunk: 费算力，但反应快
```

## 5. Action Chunk 的 50 步具体是什么？

### 格式

```
一个 Action Chunk:
  形状: [50, D]    ← 50 个时间步 × D 维动作向量
  控制频率: 20Hz → 50 步 = 2.5 秒

D 的含义 (单臂 EE 空间, D=7):
  [Δx, Δy, Δz, Δroll, Δpitch, Δyaw, gripper]
  
D 的含义 (双臂, D=14):
  [左臂 7 维, 右臂 7 维]
```

### 具体例子：抓杯子

```
  Step 1-15:  手向杯子移动 (Δx,Δy,Δz 有值, gripper=1.0 张开)
  Step 16-20: 到达上方，开始下降
  Step 21-30: 下降到位
  Step 31-35: 夹爪闭合 (gripper: 1.0 → 0.0)
  Step 36-50: 提升杯子 (Δz 为正)
```

### 单位与量纲

| 维度 | 物理含义 | 归一化范围 |
|:---|:---|:---|
| Δx, Δy, Δz | 末端位置增量 (米) | [-1,1] ≈ [-5cm, +5cm] |
| Δroll, Δpitch, Δyaw | 末端姿态增量 (弧度) | [-1,1] ≈ [-0.1rad, +0.1rad] |
| gripper | 夹爪开合度 | -1=全闭, +1=全开 |

### Flow Matching 如何生成

```
输入: 噪声 z ~ N(0, I), 形状 [50, 7]
去噪: 10 步迭代，每步让 z 更接近真实动作分布
输出: 完整 Action Chunk [50, 7]  ← 一次性全部生成 (非逐步)

类比: Stable Diffusion 一次生成整张图，Flow Matching 一次生成整条轨迹
```

### 为什么是 50 步？

```
太短 (5 步 = 0.25s): 动作不完整，推理频率太高
太长 (200 步 = 10s): 预测太远不准确，纠错太慢
50 步 (2.5s): 刚好完成一个原子动作，推理频率适中 (~0.4 次/秒)
```

## 8. 为什么 50 条 demo 就够微调？

### 核心原因：预训练学会了 95%，微调只教最后 5%

```
预训练已掌握 (10000+ 小时数据):
  ✅ 视觉理解: 物体识别、空间关系
  ✅ 运动基元: 伸手、抓取、放置、推动
  ✅ 物理直觉: 重力、碰撞、形变
  ✅ 语言理解: 指令到动作的映射
  ✅ 控制精度: 毫米级末端定位

微调只需教:
  ❓ 你的桌面布局
  ❓ 你的夹爪参数
  ❓ 你的特殊物体从哪个角度抓最好
```

### LoRA 防过拟合

```
全量微调: 50 条数据训练 5B 参数 → 严重过拟合 ❌
LoRA:    50 条数据训练 ~5M 参数 (0.1%) → 合理 ✅

数学: ΔW = AB, rank=16
  原始 W: 16M 参数/层
  LoRA:   131K 参数/层 (0.8%)
  50 条 × 50 步 = 2500 样本训练 131K 参数 → 完全够
```

### 数据量 vs 效果

| Demo 数量 | 成功率 | 适合 |
|:---|:---|:---|
| 5-10 条 | ~50% | 快速验证 |
| 50 条 | ~70% | 简单抓放 |
| 100 条 | ~85% | 标准部署 |
| 200 条 | ~90%+ | 鲁棒部署 |
| 1000+ 条 | 专家级 | 精密/工业级 |

### 类比

```
从零训练 = 教婴儿做事 (需要大量经验)
π0 微调 = 给熟练工人一个新任务说明 (几个例子就够)
```

## 11. 摄像头参数不匹配的影响

### 哪些差异有影响？

| 参数差异 | 影响 | 原因 |
|:---|:---|:---|
| 分辨率 (720p vs 1080p) | ⚠️ 低 | 模型 resize 到 224×224 |
| **FOV/焦距** (广角 vs 窄角) | ❌ 高 | 物体在画面中大小/位置全变 |
| **安装位置/角度** | ❌ 高 | 视角关系改变 |
| 色彩风格 | ⚠️ 中 | VLM 有一定鲁棒性 |
| 画质/噪声 | ⚠️ 中 | 边缘检测能力下降 |
| 帧率 | ⚠️ 低 | 按固定频率采样 |

### 为什么 FOV/角度影响最大？

```
训练时: 相机 87° FOV, 45° 俯视 → 杯子在画面中心偏右, 占 15%
推理时: 相机 120° 广角, 侧面平视 → 同一杯子在左下角, 占 5%

→ 模型学到的 "画面中杯子在右边 → 手向右伸" 全错
→ 因为画面坐标到真实世界坐标的映射变了
```

### 解决方案

| 方案 | 做法 | 效果 |
|:---|:---|:---|
| 用相同相机 | 买训练数据集用的型号 (如 RealSense D435i) | 最佳 |
| 相机标定+裁剪 | 裁剪画面到和训练时相似的 FOV | 好 |
| 数据增强微调 | 加随机裁剪/缩放/色彩抖动 | 好 |
| **采集新数据** | 用你的相机采 50 条 demo | **最稳妥** |

### 推荐

```
如果用 DROID checkpoint → 用 RealSense D435i, 基座上方 45° 俯视
如果用 ALOHA checkpoint → 标准 4 摄像头 (2 基座 + 2 腕部)
如果实在用不同相机 → 采 20-50 条 demo 微调 (最简单)
```

## 12. 所有 VLA 都能少量数据微调吗？

**不是。** 数据效率因模型架构和预训练规模差异巨大。π0 属于最数据高效的一档。

### 各 VLA 微调数据需求对比

| 模型 | 预训练数据 | 微调新任务所需 demo | 数据效率 | 原因 |
|:---|:---|:---|:---|:---|
| **π0 / π0.5** | 10,000+ 小时 | **50-200 条** | ⭐⭐⭐⭐⭐ | 超大规模预训练 + LoRA |
| **OpenVLA (7B)** | ~2,000 小时 | **200-500 条** | ⭐⭐⭐⭐ | 大 VLM 骨干 + 预训练 |
| **OpenVLA-OFT** | 同上 + OFT | **50-100 条** | ⭐⭐⭐⭐⭐ | OFT 正交微调更高效 |
| **Octo (93M)** | ~800K 条 | **500-2000 条** | ⭐⭐⭐ | 模型小，容量有限 |
| **Diffusion Policy** | 无预训练 | **2000-5000 条** | ⭐⭐ | 从零训练，无迁移知识 |
| **ACT** | 无预训练 | **50-100 条** | ⭐⭐⭐⭐ | 架构简单 + 简单任务够用 |
| **传统 BC** | 无 | **5000-50000 条** | ⭐ | 无泛化能力 |

### 决定数据效率的关键因素

```
1. 预训练规模: π0 (10000h) >> OpenVLA (2000h) >> Octo (无)
2. VLM 骨干大小: 大 VLM 从互联网学到的知识可直接迁移
3. 微调策略: LoRA/OFT (0.1% 参数) >> Full FT (100% 参数)
4. 动作空间: Flow Matching > 自回归 Binning (天然处理多模态)
5. 任务复杂度: 简单抓放 50 条够，精密插入 500 条可能不够
```

### 具体案例："在新桌面上抓杯子"

| 模型 | 50 条 | 200 条 | 500 条 | 2000 条 |
|:---|:---|:---|:---|:---|
| π0.5 + LoRA | ~75% | ~88% | ~92% | — |
| OpenVLA + LoRA | ~55% | ~78% | ~85% | — |
| Octo | ~30% | ~55% | ~60% | ~80% |
| Diffusion Policy (从零) | ~15% | ~35% | ~45% | ~82% |

### 什么时候 500 条不够？

```
即使是 π0:
  - 高度多样化物体 (50 种 → 需 1000+ 条)
  - 长程多步任务 (做拿铁 7 步 → 需 1000+ 条)
  - 高精度 (0.5mm 级 → 需 2000-5000 条)
  - 高动态 (接球 → 需数百到数千条)
```

**结论**: 能用 <500 条微调是**大规模预训练 + 参数高效微调**的红利，不是所有 VLA 都有。

## 14. 为什么 Flow Matching 动作头在少样本微调中作用突出？

结合第 8、12、13 节的数据对比与 [附录 A](./Appendix_A_Flow_Matching.md)、[22a 架构分析](./22a_Pi0_Base_Model.md) 的技术细节，Flow Matching 动作头在少样本微调中的核心优势可归纳为三点。

### 原因一：连续动作空间 → 预训练精度无损迁移

Flow Matching 直接在连续空间中建模动作值（如 `Δx = +0.0523m`），不需要像自回归 VLA（OpenVLA 等）先将动作离散化为 token bin。

```
自回归 VLA 的精度瓶颈:
  连续动作值 0.0523m → 离散化到 256 个 bin → bin #141
  → 精度上限 ≈ 动作范围 / 256 ≈ 0.4mm
  → 预训练学到的亚毫米运动基元在离散化后被截断

Flow Matching 的精度保留:
  连续动作值 0.0523m → 直接作为训练目标 (x₁)
  → 预训练学到的毫米级操作精度原样保留
  → 微调只需做 "场景适配"，而非重新学习精度
```

这意味着预训练阶段用 10,000+ 小时数据学到的精细运动技能，在微调时可以**无损继承**。50 条新数据只需要告诉模型"你的桌面长什么样"、"你的夹爪参数是什么"，而不需要重新学习"怎么精确移动到某个位置"。

### 原因二：多模态分布建模 → 少量数据不会 "平均化"

这是 [第 12 节](#12-所有-vla-都能少量数据微调吗) 中"关键因素第 4 条"指出的核心：`Flow Matching > 自回归 Binning (天然处理多模态)`。

```
问题场景: 杯子在障碍物后面，可以从左绕或从右绕

50 条 demo 中:
  25 条从左绕 → 动作序列偏左
  25 条从右绕 → 动作序列偏右

回归 / 自回归头 (MSE 损失):
  输出 = (左路径 + 右路径) / 2 = 中间路径 → 撞上障碍物 ❌
  → 数据越少，mode averaging 越致命

Flow Matching (生成式模型):
  学到完整的双峰分布 p(action | observation)
  每次采样从某一个峰采出一条完整可行轨迹 ✅
  → 即使只有 50 条 demo 覆盖了两种策略，也能正确建模
```

少量数据场景下，动作分布的多模态性（多种合理路径）更难通过"取均值"消除。Flow Matching 作为生成式模型天然具备多模态建模能力，因此在少样本场景下优势被放大。

### 原因三：Action Expert 独立参数 → 微调时的分工隔离

从 [第 13 节](#13-π0-系列各版本参数量) 的架构分布可以看到：

```
π0.6 参数分布:
  VLM 骨干 (SigLIP + Gemma3 4B):  ~4,400M (83%)  ← 冻结或轻微调
  Action Expert (Flow Matching):  ~860M (16%)    ← 微调重点
  Projector/Adapter:              ~40M (1%)      ← 微调重点

微调策略: LoRA rank=16
  原始 Action Expert 每层: ~16M 参数
  LoRA 每层:              ~131K 参数 (0.8%)
  50 条 × 50 步 = 2,500 个训练样本 → 训练 131K 参数 → 完全合理
```

Flow Matching 动作头作为独立模块，允许微调时的**精确分工**：
- **VLM 骨干保持冻结**：保留预训练的视觉语义知识（"这是杯子"、"杯子在桌面右侧"）
- **Action Expert 重点微调**：适配新场景的运动细节（"你的桌面高度"、"你的夹爪开合范围"）

这种分工在自回归架构中更难实现——因为自回归 VLA 的动作 token 和语言 token 共享同一个 Transformer decoder，很难只调动作部分而不影响语义理解。

### 50 条 demo 成功率对比佐证

| 模型 | 动作头类型 | 50 条 demo 成功率 | 差距来源 |
|:---|:---|:---|:---|
| **π0.5 + LoRA** | Flow Matching | **~75%** | 上述三点叠加 |
| OpenVLA + LoRA | 自回归 Binning (256 bin) | ~55% | 离散化损精度 + mode averaging |
| Diffusion Policy | DDPM (从零训练) | ~15% | 无预训练知识，去噪步数多 |
| ACT | 确定性回归 | ~50%\* | 简单任务够用，复杂任务 mode averaging |

> \* ACT 在简单抓放任务上数据效率尚可，但在需要多模态决策的复杂任务上迅速劣化。

### 一句话总结

```
Flow Matching 在少样本微调中的优势 =
  连续精度无损迁移 (不离散化)
  + 多模态分布正确建模 (不取均值)
  + 独立 Action Expert 支持精确分工微调 (不干扰 VLM)
  → 50 条 demo 即可达到 ~75% 成功率
```

> 详细 Flow Matching 数学推导参见 [附录 A](./Appendix_A_Flow_Matching.md)；预训练数据规模对数据效率的贡献参见 [第 8 节](#8-为什么-50-条-demo-就够微调) 和 [第 12 节](#12-所有-vla-都能少量数据微调吗)。

## 15. SigLIP ViT-SO400M 与普通 ViT 的区别

### 训练目标对比

| 维度 | 普通 ViT (ImageNet) | CLIP ViT | **SigLIP ViT** |
|:---|:---|:---|:---|
| 损失函数 | Cross-Entropy 分类 | Softmax 对比损失 (InfoNCE) | **Sigmoid 对比损失** |
| 标签来源 | 人工标注类别 | 图文对 | 图文对 |
| 负样本机制 | 无 | batch 内全对比 (需 all-gather) | **逐对独立 sigmoid** |

SigLIP 用 sigmoid 替代 softmax，每对图文独立判断"匹配/不匹配"，不需要跨 GPU 计算全局 softmax 分母 → **训练效率大幅提升**，可以用更大 batch size。

### "SO400M" 命名含义

- **S** = Shape-Optimized（形状优化，不是标准 ViT-B/L/H 尺寸）
- **O** = 特殊架构配置
- **400M** = 总参数约 4 亿

### 架构参数对比

| 模型 | 参数 | hidden_dim | layers | heads | patch_size |
|:---|:---|:---|:---|:---|:---|
| ViT-B/16 | 86M | 768 | 12 | 12 | 16 |
| ViT-L/14 | 304M | 1024 | 24 | 16 | 14 |
| ViT-H/14 | 632M | 1280 | 32 | 16 | 14 |
| **SigLIP SO400M/14** | **~400M** | **1152** | **27** | **16** | **14** |

SO400M 介于 ViT-L 和 ViT-H 之间，是 Google 用 NAS/scaling law 搜索出来的最优配置。

### 训练数据

| 模型 | 训练数据 |
|:---|:---|
| 普通 ViT | ImageNet-1K/21K (~1-14M 图片) |
| CLIP ViT | WebImageText 400M 对 |
| **SigLIP SO400M** | **WebLI (Web Language-Image) ~10B 图文对** |

### 输出特性

| 特性 | 普通 ViT | SigLIP |
|:---|:---|:---|
| 输出 | 类别 logits | **图像嵌入向量** (语义对齐到文本空间) |
| 下游用法 | 加分类头微调 | 直接做零样本分类 / 作为 VLM 视觉编码器 |
| 语义丰富度 | 仅 ImageNet 类别 | 自然语言级语义 (颜色、材质、动作、空间关系...) |

### 为什么 π0 选 SigLIP SO400M

```
1. 语义丰富: 10B 图文对预训练 → 理解自然语言指令中描述的物体/场景
2. 参数高效: 400M (vs CLIP ViT-H 632M) 性能相当但更轻
3. 分辨率灵活: 支持 224/384/512 输入，NaViT 变长序列
4. 训练稳定: sigmoid 损失不需要 temperature learnable parameter
5. 与 Gemma 对齐: Google 自家生态，PaliGemma = SigLIP + Gemma
```

## 16. 不同 ViT 对 VLA 效果的影响

### OpenVLA 消融实验 (2024)

| 视觉编码器 | 参数 | 预训练数据 | VLA 成功率 (SimplerEnv) |
|:---|:---|:---|:---|
| ViT-B/16 (ImageNet) | 86M | 1.2M 图片 | ~32% |

### RT-2 系列的发现

| 配置 | 视觉编码器 | 成功率 |
|:---|:---|:---|
| RT-2 (12B) | ViT-G/14 (1.8B, CLIP) | ~65% |

### 影响因素分解

| 因素 | 影响程度 | 原因 |
|:---|:---|:---|
| **预训练数据类型** | ⭐⭐⭐⭐⭐ | 图文对比 > 纯分类 > 自监督。VLA 需要语言对齐的视觉特征 |
| **预训练数据量** | ⭐⭐⭐⭐ | 10B 对 (SigLIP) >> 400M 对 (CLIP) >> 14M (ImageNet-21K) |
| **模型大小** | ⭐⭐⭐ | 有收益但边际递减：86M→400M 提升巨大，400M→1.8B 提升有限 |
| **输入分辨率** | ⭐⭐⭐⭐ | 224→384→512 对操控任务帮助很大（抓取精度） |
| **Patch size** | ⭐⭐⭐ | 14→16 影响不大；14→32 会显著降低精细操控 |
| **是否冻结** | ⭐⭐ | 微调 ViT 在小数据上易过拟合，冻结+projector 更稳定 |

### 不同 ViT 的特征差异

```
ImageNet ViT:    "这是一个杯子" (类别级)
CLIP ViT:        "一个白色陶瓷咖啡杯放在木桌上" (描述级)
SigLIP ViT:      "一个白色陶瓷咖啡杯放在木桌右侧，把手朝左" (描述+空间级)
DINOv2 ViT:      精确的纹理/边缘/深度特征，但缺乏语言对齐
```

### 不同任务对 ViT 的需求

| 任务 | 需要什么特征 | 最适合的 ViT |
|:---|:---|:---|
| "抓住红色杯子" | 颜色+物体识别 | CLIP / SigLIP |
| "把杯子放到盘子右边" | 空间关系 | SigLIP (大数据量，更好的空间理解) |
| "插入 USB 接口" | 高精度几何 | DINOv2 + SigLIP 双编码器 |
| "叠衣服" | 形变物体理解 | SigLIP (语义) + 高分辨率 |

### 双视觉编码器趋势

| 模型 | 语义编码器 | 空间编码器 | 效果 |
|:---|:---|:---|:---|
| Theia (2024) | SigLIP | DINOv2 | +12% (vs 单 SigLIP) |
| HPT (2024) | CLIP | DINOv2 | +9% |
| **π0.6** | SigLIP SO400M | — (Action Expert 补偿) | 足够好 |

### 定量总结

```
从 ImageNet ViT-B → SigLIP SO400M:     +30~40% 成功率
从 CLIP ViT-L → SigLIP SO400M:         +5~15% 成功率
从 SigLIP SO400M → ViT-G (1.8B):       +2~5% 成功率 (不值得)
从 224px → 384px (同 ViT):              +8~15% 成功率
加 DINOv2 双编码器:                      +5~12% 成功率
```

> **结论**：视觉编码器的预训练数据类型和规模 >> 模型大小。SigLIP SO400M 是当前 VLA 的最优性价比选择。

## 17. 推理时如何判断任务完成？

π0 本身**不内置任务完成检测**，它持续预测 Action Chunk 直到外部系统告诉它停止。

### 四种方式

| 方法 | 原理 | 优点 | 缺点 |
|:---|:---|:---|:---|
| **固定时长截断** | 预设最大执行时间（30-60秒） | 简单 | 浪费时间或超时 |
| **动作幅度阈值** | 所有动作增量趋近零 → 停止 | 无需额外模型 | 连续输出难精确为零 |
| **外部检测器** | 独立视觉模型/传感器判断成功 | 准确 | 需额外部署 |
| **VLM 语言输出 (π0.5)** | 模型输出 "done" 文本 | 端到端 | 需模型支持多模态输出 |

论文中大部分 benchmark 实验使用**固定时长截断**（每个任务有固定 episode 时间上限）。

## 18. Flow Matching 1 步去噪的优缺点

### 1 步去噪含义

直接从噪声一步跳到动作：$a_1 = a_0 + v_\theta(a_0, 0, h)$，不做中间迭代。

### 优点

| 优点 | 说明 |
|:---|:---|
| 极低延迟 | 只需 1 次 Cross-Attention + FFN_action（~2.5ms），总延迟 ~17ms |
| 硬实时控制 | 满足 >50Hz 的高频控制需求 |
| 简化部署 | 无循环逻辑，适合嵌入式设备 |

### 缺点

| 缺点 | 说明 |
|:---|:---|
| 精度下降 | 速度场只在 $t=0$ 评估一次，积分误差最大 |
| 多模态退化 | 10 步让噪声有机会"分流"到不同模态，1 步只走一条 → mode averaging |
| 复杂轨迹失真 | 非线性轨迹（S 形绕障）无法用单步线性近似 |
| 训练-推理不匹配 | 网络在 $t \in [0,1]$ 上都训练过，但 1 步推理只用了 $t=0$ |

### 经验数据

```
步数   简单抓取成功率   精密操作成功率
1步     ~85%            ~40%        ← 精密操作大幅下降
5步     ~92%            ~75%
10步    ~95%            ~88%        ← π0 默认
20步    ~95%            ~90%        ← 收益递减
```

**结论**：1 步适合简单快速任务；π0 目标场景（缝纫、插销等精密操作）需要 10 步。

## 19. π0 完整训练流程（4 阶段）

### 阶段 1：SigLIP ViT 预训练（Google 完成）

- **目标**：学会"看懂图片"——图文语义对齐
- **数据**：WebLI ~10B 图文对（互联网图片+描述）
- **方法**：Sigmoid 对比学习
- **产出**：ViT-SO400M (~400M 参数)
- **备注**：Physical Intelligence 直接用 Google 开源权重

### 阶段 2：VLM 预训练（Google 完成 → PaliGemma/Gemma3）

- **目标**：学会"看图说话"——视觉问答、图像描述
- **架构**：SigLIP + Projector + Gemma 2B/4B
- **方法**：Stage 2a 冻结 ViT 训练 Projector+LLM → Stage 2b 全解冻联合微调
- **产出**：PaliGemma / Gemma3 VLM
- **备注**：PI 直接用 Google 开源权重（可能做少量领域适配续训）

### 阶段 3：π0 VLA 预训练（Physical Intelligence 核心工作）

- **目标**：学会"看图做事"——从视觉+语言生成动作
- **架构改动**：在 VLM 每层插入 Action Expert（新增 ~860M 随机初始化参数）
- **数据**：OXE (~1M 条轨迹) + DROID (~76K) + PI 自有数据，总计 ~10M+ 图像-动作对
- **损失**：$\mathcal{L} = \mathcal{L}_{\text{FM}} + \lambda \cdot \mathcal{L}_{\text{LM}}$（语言建模可选）
- **训练细节**：256-512×H100，batch ~2048，VLM 用小学习率（0.1-0.5×），Action Expert 用正常学习率
- **产出**：π0 Base Model

### 阶段 4：任务微调（用户/部署方）

- **目标**：特定任务高成功率
- **数据**：5-100 条演示轨迹
- **推荐方法**：冻结 VLM，只微调 Action Expert (~860M)
- **训练时间**：数小时（单卡/少量 GPU）
- **为什么有效**：VLM "看懂场景"已足够，只需调整"怎么动"

```
参数冻结状态:
         阶段1   阶段2a  阶段2b  阶段3    阶段4(推荐)
ViT:     🔓训练   ✅冻结   🔓解冻   🔓微调    ✅冻结
Proj:     —       🔓训练   🔓解冻   🔓微调    ✅冻结
LLM:      —       🔓训练   🔓解冻   🔓微调    ✅冻结
AE:       —        —       —      🔓训练    🔓训练
```

## 20. VLA 预训练后 VLM 原始能力是否保留？

### 核心结论

**VLA 预训练几乎必然损害 VLM 通用能力**，程度取决于设计策略。

### 各模型表现

| 模型 | VLM 测试 | 结果 | 设计策略 |
|:---|:---|:---|:---|
| **RT-2** | ✅ VQA | 基本保留（下降 <2%） | 动作表示为文本 token |
| **OpenVLA** | ✅ VQA | 显著下降（-10~15%） | 全参数微调 |
| **RT-2-X** | ✅ 多 benchmark | 基本保留 | 大模型 (55B) + 混合训练 |
| **π0** | ❌ 未测试 | 未知 | Action Expert 独立参数 |
| **π0.5** | 部分 | 可输出语言 | FM + LM 联合训练 |

### 防遗忘策略

1. **动作即语言**（RT-2）：动作和语言共享输出空间，训练目标一致
2. **独立参数**（π0）：Action Expert 独立 FFN 减少互相干扰
3. **混合训练**（π0.5）：加入语言建模损失 $\mathcal{L}_{\text{LM}}$
4. **大模型 buffer**（RT-2-X）：55B 参数有足够容量编码两种能力
5. **数据混合**：训练时混合原始 VLM 数据 + 机器人数据

### 是否必须保留？

**不是**。如果场景是固定任务、有充足数据、不需要语言交互或调试，VLM 能力完全可以牺牲。

保留 VLM 能力的实用价值：
- **调试**：问模型"你看到了什么"快速定位感知 vs 动作问题
- **任务终止**：模型输出 "done" 作为停止信号（π0.5）
- **零样本泛化**：理解从未训练过的指令语义
- **减少微调数据**：VLM 已"看懂"场景，只需学"怎么动"

## 21. 摄像头型号差异对 π0 的影响

π0 **不需要**在 prompt 中告知摄像头内外参数或型号。

### 处理机制

1. **训练数据多样性**：预训练数据来自 7+ 种机器人、数十种摄像头配置（Intel RealSense、ZED Mini、Logitech C920 等），模型学会从像素直接推断空间关系
2. **Token 位置隐式区分视角**：基座/腕部图像按固定顺序拼接，模型通过相对位置区分
3. **本体感受弥补内参差异**：不同 FOV 导致物体大小不同，但本体感受提供绝对空间参考
4. **SigLIP 多分辨率支持**：NaViT 直接处理不同分辨率输入

### 哪些情况需要额外处理？

| 场景 | 处理方式 |
|:---|:---|
| 换同类型摄像头（C920→C922） | 不需要处理，resize 即可 |
| 安装位置大幅改变 | 需微调（收集新视角演示） |
| 增/减摄像头数量 | 需重新训练（Token 序列含义变了） |
| 分辨率改变（224→512） | 不需要（SigLIP+NaViT 支持） |
| 视角类型完全变化（侧面→俯视） | 需微调 |

## 22. 机械臂型号/参数改变时如何处理？

### 核心原则

机械臂身份由**本体感受 Token 隐式传达**，不需要文本 prompt 显式告知。

### 本体感受 = 机械臂"身份证"

```
Franka (7-DOF):  [q1..q7, dq1..dq7, gripper]  → 15维
UR5e (6-DOF):    [q1..q6, dq1..dq6, gripper]  → 13维
ALOHA (双臂):    [qL1..qL7, qR1..qR7, ...]    → 30维
```

模型从关节角度的数值范围和维度"认出"是哪种机械臂。

### 换臂策略

| 变化类型 | 数据量 | 处理方式 |
|:---|:---|:---|
| 同型号换个体 | 0条 | 直接用 |
| DOF 相同，臂长/负载变化 | 20-50条 | 微调 Action Expert |
| DOF 数量改变 | 100-200条 | 微调 + 调本体 MLP |
| 完全不同形态（单→双臂） | 500-1000条 | 较大规模微调 |

### 微调方法：Action Expert Fine-tuning

```
冻结: SigLIP + Gemma (整个 VLM, ~4.4B)
解冻: FFN_action (~860M) + 本体感受 MLP

训练配置:
  损失: Flow Matching 标准损失
  学习率: ~1e-5
  Batch: 8-32
  硬件: 单卡 A100/4090
  时间: 2-6 小时
  早停: 防过拟合
```

### 为什么数据量需求小？

```
机器人操作 = ① 理解场景 + ② 规划策略 + ③ 执行动作

① 理解场景 → VLM 已学会 (冻结, 不需要重新学)
② 规划策略 → 预训练已学会 (抓取流程通用)
③ 执行动作 → 需要适配 (只调 Action Expert)

换臂只需要学 ③:
  "在新臂上，往右移5cm 对应什么关节增量？"
  → 低维确定性映射，50-100条即可拟合

类比: 会骑自行车的人换一辆新车 → 不需要重新学骑车，
     只需几分钟适应"把手灵敏度/踏板阻力"
```

### 关键限制

微调有效的前提：
- 新臂的目标任务在预训练任务分布内
- 视觉输入格式与预训练一致
- 动作空间语义兼容（笛卡尔/关节空间）
