## 1. 能否在消费级显卡上运行？

### 参数量与显存需求

```
π0.7 核心组件:
  VLM 骨干 (SigLIP + Gemma3 4B):  ~4B 参数
  Action Expert (Flow Matching):   ~860M 参数
  高层策略 (VLM 复用):             共享参数
  世界模型 (轻量级):               ~数百M (估算)
  总计: ~5-6B 参数
```

| 精度 | 模型显存 | KV Cache + 推理 | 总需求 |
|:---|:---|:---|:---|
| FP16/BF16 | ~11 GB | ~4 GB | ~15 GB |
| INT8 量化 | ~5.5 GB | ~3 GB | ~8.5 GB |
| INT4 量化 | ~3 GB | ~2.5 GB | ~5.5 GB |

### 消费级显卡可行性

| 显卡 | 显存 | FP16 | INT8 | INT4 |
|:---|:---|:---|:---|:---|
| RTX 3060 (12GB) | 12 GB | ❌ | ✅ 勉强 | ✅ |
| RTX 3090 (24GB) | 24 GB | ✅ | ✅ | ✅ |
| RTX 4060 Ti (16GB) | 16 GB | ✅ 勉强 | ✅ | ✅ |
| RTX 4090 (24GB) | 24 GB | ✅ | ✅ | ✅ |
| RTX 5090 (32GB) | 32 GB | ✅ 充裕 | ✅ | ✅ |

### 关键瓶颈：推理速度

```
消费级 vs 服务器级推理延迟:
  RTX 4090:     ~80ms/step  → ~12Hz  → 勉强可用 (Action Chunk 缓冲)
  RTX 3060:     ~200ms/step → ~5Hz   → 太慢
  A100/H100:    ~30ms/step  → ~33Hz  → 充裕

Action Chunking 的救命作用:
  每次推理输出 50 步动作 (约 2-3 秒)
  → 即使推理 100ms/次，实际控制频率相当于 ~500Hz
  → 关键是 chunk 间的平滑衔接
```

### 已有先例

OpenPi (π0/π0-FAST/π0.5 开源版) 支持 RTX 4090 推理：
- FP16: ~15Hz
- INT8: ~20Hz
- 官方最低要求: >8GB 显存 (推理), >22.5GB (LoRA 微调)

## 2. 量化对 VLA 性能的影响

### VLA 比 LLM 更怕量化

```
LLM 输出: 离散 token (从 32000 词中选一个)
  → 量化误差只要不改变 argmax 排序，输出完全不变
  → 对量化非常鲁棒

VLA 输出: 连续动作值 (如 Δx = +0.0523m)
  → 量化误差直接叠加到动作值上
  → 0.5mm 偏差在精细操作中可能导致失败
```

### 量化性能数据 (基于 OpenVLA 等开源 VLA)

| 模型 | 精度 | 简单任务 (抓取) | 中等任务 (放置) | 精细任务 (插入) |
|:---|:---|:---|:---|:---|
| FP16 基线 | — | 85% | 72% | 45% |
| INT8 | 8-bit | 84% (-1%) | 70% (-2%) | 40% (-5%) |
| INT4 | 4-bit | 80% (-5%) | 62% (-10%) | 28% (-17%) |

### 关键发现：Action Expert 是量化瓶颈

```
VLM 骨干 (语义特征): 量化鲁棒性好，INT4 损失 <3%
Action Expert (连续动作值): 对量化极其敏感

最佳实践 — 混合精度量化:
  VLM 骨干 → INT4 (省显存)
  Action Expert → FP16 或 INT8 (保精度)
  → 总显存 ≈ INT8 水平，精细任务性能接近 FP16
```

### FAST 架构天然抗量化

```
Flow Matching (π0 原版):
  10 步迭代去噪 → 量化误差累积 → INT4 性能下降明显

FAST 自回归 (π0-FAST):
  输出离散 token → 量化不改变 token 排序就无损
  → INT4 也几乎无损 ← 边缘部署首选
```

## 3. 云端 GPU 推理方案与成本

### 核心矛盾：延迟

```
云端推理延迟链:
  上传图像 (~5-20ms) → 网络传输 (~10-50ms) → GPU 推理 (~30-80ms) → 下发动作 (~5-20ms)
  总计: 50-170ms (理想) / 100-300ms (现实)

Action Chunking 补偿:
  一次推理输出 50 步 (2.5 秒) → 执行期间不需要网络通信
  → 对折叠、擦桌等非时间关键任务完全 OK
```

### 服务商价格对比

| 服务商 | GPU | 价格 | 适合 |
|:---|:---|:---|:---|
| **AutoDL** (国内) | RTX 4090 | ~¥2-3/时 | 国内研究首选 |
| **AutoDL** | A100 | ~¥8-12/时 | 国内高性能 |
| **RunPod** | RTX 4090 | ~$0.4-0.7/时 | 海外低价 |

```

3. 就近部署: 同城数据中心 <10ms RTT
4. TensorRT/ONNX 优化: 推理速度翻倍
```

## 4. 为什么机器人控制需要低延迟？

### 能暂停等推理吗？

**部分任务可以，但物理世界不会暂停。**

| 可以等 ✅ | 不能等 ❌ |
|:---|:---|
| 静态环境操作 (折叠、擦桌) | 接住抛来的物体 (~550ms 总时间) |
| 物体不会自己移动的场景 | 倒水 (暂停时水继续流) |
| 步骤间有自然停顿的任务 | 搬运易碎品 (停顿→抖动→洒出) |
| | 人机交互 (人期望 <0.5s 响应) |

### π0 的解法：Action Chunking = "有计划的暂停"

```
时序:
  t=0ms:      推理开始
  t=80ms:     推理完成，得到 50 步 Action Chunk
  t=80-2080ms: 以 50Hz 连续执行 (不需要推理)
  t=1800ms:   提前开始推理下一个 chunk (pipeline)
  t=2080ms:   无缝切换到新 chunk
  
  → 机器人连续运动，"暂停"被隐藏在执行期间
```

### Action Chunking 的局限

```
环境变化速度 > chunk 更新速度时:
  chunk 规划 "向前伸手 50 步" → 第 10 步时人把物体移走
  → 第 11-50 步按原计划执行 → 抓空
  → 需要等下一个 chunk 才能反应

tradeoff:
  长 chunk: 省算力，但反应慢
  短 chunk: 费算力，但反应快
```

## 5. Action Chunk 的 50 步具体是什么？

### 格式

```
一个 Action Chunk:
  形状: [50, D]    ← 50 个时间步 × D 维动作向量
  控制频率: 20Hz → 50 步 = 2.5 秒

D 的含义 (单臂 EE 空间, D=7):
  [Δx, Δy, Δz, Δroll, Δpitch, Δyaw, gripper]
  
D 的含义 (双臂, D=14):
  [左臂 7 维, 右臂 7 维]
```

### 具体例子：抓杯子

```
  Step 1-15:  手向杯子移动 (Δx,Δy,Δz 有值, gripper=1.0 张开)
  Step 16-20: 到达上方，开始下降
  Step 21-30: 下降到位
  Step 31-35: 夹爪闭合 (gripper: 1.0 → 0.0)
  Step 36-50: 提升杯子 (Δz 为正)
```

### 单位与量纲

| 维度 | 物理含义 | 归一化范围 |
|:---|:---|:---|
| Δx, Δy, Δz | 末端位置增量 (米) | [-1,1] ≈ [-5cm, +5cm] |
| Δroll, Δpitch, Δyaw | 末端姿态增量 (弧度) | [-1,1] ≈ [-0.1rad, +0.1rad] |
| gripper | 夹爪开合度 | -1=全闭, +1=全开 |

### Flow Matching 如何生成

```
输入: 噪声 z ~ N(0, I), 形状 [50, 7]
去噪: 10 步迭代，每步让 z 更接近真实动作分布
输出: 完整 Action Chunk [50, 7]  ← 一次性全部生成 (非逐步)

类比: Stable Diffusion 一次生成整张图，Flow Matching 一次生成整条轨迹
```

### 为什么是 50 步？

```
太短 (5 步 = 0.25s): 动作不完整，推理频率太高
太长 (200 步 = 10s): 预测太远不准确，纠错太慢
50 步 (2.5s): 刚好完成一个原子动作，推理频率适中 (~0.4 次/秒)
```

## 8. 为什么 50 条 demo 就够微调？

### 核心原因：预训练学会了 95%，微调只教最后 5%

```
预训练已掌握 (10000+ 小时数据):
  ✅ 视觉理解: 物体识别、空间关系
  ✅ 运动基元: 伸手、抓取、放置、推动
  ✅ 物理直觉: 重力、碰撞、形变
  ✅ 语言理解: 指令到动作的映射
  ✅ 控制精度: 毫米级末端定位

微调只需教:
  ❓ 你的桌面布局
  ❓ 你的夹爪参数
  ❓ 你的特殊物体从哪个角度抓最好
```

### LoRA 防过拟合

```
全量微调: 50 条数据训练 5B 参数 → 严重过拟合 ❌
LoRA:    50 条数据训练 ~5M 参数 (0.1%) → 合理 ✅

数学: ΔW = AB, rank=16
  原始 W: 16M 参数/层
  LoRA:   131K 参数/层 (0.8%)
  50 条 × 50 步 = 2500 样本训练 131K 参数 → 完全够
```

### 数据量 vs 效果

| Demo 数量 | 成功率 | 适合 |
|:---|:---|:---|
| 5-10 条 | ~50% | 快速验证 |
| 50 条 | ~70% | 简单抓放 |
| 100 条 | ~85% | 标准部署 |
| 200 条 | ~90%+ | 鲁棒部署 |
| 1000+ 条 | 专家级 | 精密/工业级 |

### 类比

```
从零训练 = 教婴儿做事 (需要大量经验)
π0 微调 = 给熟练工人一个新任务说明 (几个例子就够)
```

## 11. 摄像头参数不匹配的影响

### 哪些差异有影响？

| 参数差异 | 影响 | 原因 |
|:---|:---|:---|
| 分辨率 (720p vs 1080p) | ⚠️ 低 | 模型 resize 到 224×224 |
| **FOV/焦距** (广角 vs 窄角) | ❌ 高 | 物体在画面中大小/位置全变 |
| **安装位置/角度** | ❌ 高 | 视角关系改变 |
| 色彩风格 | ⚠️ 中 | VLM 有一定鲁棒性 |
| 画质/噪声 | ⚠️ 中 | 边缘检测能力下降 |
| 帧率 | ⚠️ 低 | 按固定频率采样 |

### 为什么 FOV/角度影响最大？

```
训练时: 相机 87° FOV, 45° 俯视 → 杯子在画面中心偏右, 占 15%
推理时: 相机 120° 广角, 侧面平视 → 同一杯子在左下角, 占 5%

→ 模型学到的 "画面中杯子在右边 → 手向右伸" 全错
→ 因为画面坐标到真实世界坐标的映射变了
```

### 解决方案

| 方案 | 做法 | 效果 |
|:---|:---|:---|
| 用相同相机 | 买训练数据集用的型号 (如 RealSense D435i) | 最佳 |
| 相机标定+裁剪 | 裁剪画面到和训练时相似的 FOV | 好 |
| 数据增强微调 | 加随机裁剪/缩放/色彩抖动 | 好 |
| **采集新数据** | 用你的相机采 50 条 demo | **最稳妥** |

### 推荐

```
如果用 DROID checkpoint → 用 RealSense D435i, 基座上方 45° 俯视
如果用 ALOHA checkpoint → 标准 4 摄像头 (2 基座 + 2 腕部)
如果实在用不同相机 → 采 20-50 条 demo 微调 (最简单)
```
